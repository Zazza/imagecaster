# Imagecaster — Алгоритмы и потоки данных

Приложение само не генерирует ни картинки, ни текст. Вся работа уходит на **Imagecaster Server** (настройка `server_url`):

| Путь на сервере | Движок | Для чего |
|---|---|---|
| `/api/llm/v1/chat/completions` | llama.cpp | текст: промпт из идеи, промпт образа, рецепты |
| `/api/llm/api/chat` (с картинкой) | llama.cpp (vision-модель) | описание фото, теги, определение объекта |
| `/api/sd/jobs` | stable-diffusion.cpp | каждая картинка: txt2img, img2img, апскейл |
| `/api/sd/memory` | — | свободная VRAM/RAM для защиты памяти |

Код: `internal/generation` (алгоритмы), `internal/sd` (клиент заданий), `internal/llm` (клиент LLM), `internal/queue` (очередь приложения), `internal/preset/history.go` (галерея).

## 1. Генерация по тексту

```
Фронтенд            Приложение (generation)        Сервер: llama.cpp       Сервер: sd.cpp
   │ GenerateImage /   │                                  │                      │
   │ EnqueueTxt        │                                  │                      │
   │──────────────────>│ есть идея?                       │                      │
   │                   │  GenerateSDPrompt ──────────────>│ chat completion      │
   │                   │  <────────── промпт + негатив ───│                      │
   │                   │ промпт: пресет + текст LLM       │                      │
   │                   │   + теги <lora:имя:вес>          │                      │
   │                   │ защита памяти (может выгрузить LLM) ─>│                 │
   │                   │ POST /api/sd/jobs  kind=txt2img, model=ModelSpec ──────>│
   │                   │ опрос задания раз в 1 с (прогресс) ────────────────────>│
   │                   │ <──────────────────────────────────────── картинки ─────│
   │                   │ сохранение в сессию (data/sessions/<id>/)               │
   │<── результат ─────│                                                          │
```

**Промпт из идеи** (`GenerateSDPrompt`):

1. Детский режим фильтрует текст пользователя (запрещённые слова → ошибка) и добавляет правила в системный промпт.
2. Системный промпт = `sd_prompt_instruction` (теги) или, для «прозаических» моделей, `sd_prompt_instruction_prose`. Прозаические — модели, в имени которых есть flux, z-image, klein, qwen-image, chroma, hunyuan, krea и подобные (полный список: `config.NewGenModelFamilies`). В конец добавляются правило про текст на картинке и строка о длине ответа (`llm_max_tokens`).
3. Сообщение пользователя: промпт и негатив пресета как образец стиля (не копировать), затем сцена и негатив пользователя.
4. Ответ разбирается (JSON `{prompt, negative_prompt}` или обычный текст) и чистится: кириллица вне кавычек убирается, мусор и повторы удаляются, примеры из инструкции вырезаются, длина ограничивается (1000 символов для теговых моделей, 2000 для прозаических), применяется выходной фильтр детского режима.

**Запрос картинки**: из пресета берутся сэмплер и планировщик (имена sd.cpp), шаги, CFG, seed, clip skip, батч, VAE. Размер — из выбранного разрешения или пресета. `ModelSpec` = чекпоинт + VAE + модули (файлы текстового энкодера/VAE, нужные модели: для Klein — встроенный список, иначе — из каталога сервера).

**Hires fix**: профиль hires добавляет второй проход внутри того же задания txt2img. Если задание с hires упало, приложение ждёт 3 с, генерирует без hires, затем само делает апскейл и повторный проход img2img. Если и это не вышло, возвращается обычная картинка с пометкой «hires пропущен».

## 2. Жизненный цикл задания SD

Каждый запрос картинки — одно задание на сервере (`internal/sd/jobs.go`):

1. `POST /api/sd/jobs` с `kind`, `client`, `client_ref`, `model`, `params`. Сетевая ошибка при отправке повторяется до 3 раз с паузой 1 с; HTTP-ошибка от сервера не повторяется.
2. Приложение раз в секунду опрашивает `GET /jobs/<id>` и передаёт прогресс в интерфейс.
3. `completed` → забирает результат. Прямые (не из очереди) задания после этого удаляются на сервере.
4. `lost`, `failed` с кодом `server_restarted` (сервер перезапустился посреди задания) или 404 → то же задание отправляется ещё раз; вторая потеря — ошибка.
5. «Прервать» снимает локальные ожидания и отменяет на сервере все незавершённые задания, у которых `client_ref` начинается с id этой установки.

Сервер возвращает уже существующее задание, если тот же клиент прислал тот же `client_ref`, пока старое задание в очереди, выполняется или завершено. Результаты заданий сервер хранит 24 часа.

## 3. Пайплайны (составные пресеты)

Пайплайн — упорядоченный список шагов; у шага есть пресет, сила denoise, необязательная замена LoRA и необязательное разрешение (`compound_preset_steps`). Режим «Конструктор» отправляет такие же шаги без сохранения.

```
идея / текст сцены ──LLM──> промпт сцены (в стиле пресета шага 1)
шаг 1: txt2img   (пресет 1 + промпт сцены)               ──> картинка 1
шаг 2: img2img   (пресет 2, исходник = картинка 1, denoise) ──> картинка 2
...
последний шаг: профиль hires (внутри задания, если шаг один,
               иначе апскейл + img2img после последнего шага)
```

- Каждый шаг проходит защиту памяти для своей модели и идёт отдельным заданием со своей моделью.
- Элемент сессии хранит цепочку (шаг, пресет, модель, denoise, LoRA) в `meta.chain`.

## 4. Из изображения / Ремикс

Карточка «Ремикс» (Постобработка) и поток «из изображения» вызывают `GenerateFromImage`.

**Сначала описание фото** (`AnalyzeImage`, локальная vision-модель через llama.cpp):

| Режим | Настройка промпта | Результат |
|---|---|---|
| по умолчанию (теги) | `analyze_system_prompt` + `analyze_prompt` | теги через запятую, без дублей |
| `describe` | `analyze_describe_prompt` | описание прозой |
| `garment` | `edit_garment_prompt` | только описание одежды |

**Генерация** (`GenerateFromImage`):

| Параметр | Что делает |
|---|---|
| `mode=txt2img` | фото нужно только для описания; генерируется новая картинка |
| `mode=img2img` | фото — исходник; `denoising_strength` 0–1 |
| `gen_mode=preset` / `compound` | один пресет или пайплайн, первый шаг которого стартует от фото |
| есть теги | LLM превращает теги в промпт для пресета (для img2img — с указанием «преврати в эту сцену»); тегов нет → только промпт пресета, без LLM |
| `preserve_identity` | только модели Klein, img2img с пресетом, denoise ≤ 0.9: фото дополнительно уходит как референс (`klein_reference` → `ref_images` в sd.cpp) |
| `output_mode=quality` | нужно разрешение: апскейл до цели, затем лёгкий проход img2img; при сбое шаг пропускается и помечается |
| маска | только img2img с пресетом: результат вклеивается в оригинал только внутри маски (`maskcomp.Blend`); для пресетов материала/узора vision-модель сначала называет объект под маской, и промпт строится вокруг него |
| сохранить цвет | пресеты материала: возвращаются исходные цвета (`maskcomp.KeepColor`) |

С моделью Klein и без выбранного разрешения img2img идёт примерно в 1 Мп (`kleinWorkSize`); размер результата — размер фото, поднятый до 1024 px по длинной стороне, если он меньше.

## 5. Операции постобработки

Все используют `flux-2-klein-4b` с исходным фото как референсом, если не сказано иначе.

| Карточка | Алгоритм |
|---|---|
| **Эффект** | задание очереди `from_image`: img2img с пресетом эффекта, `preserve_identity=true`, выбранная сила; с маской — вклейка только внутри маски |
| **Образ** (стиль текстом) | LLM превращает описание образа в английский промпт на 1–2 предложения (2 попытки) → Klein img2img с заданной силой примерно в 1 Мп → апскейл до исходного размера |
| **Правка** | инструкция (+ теги стиля/LoRA из пресета стиля, если выбраны) → Klein img2img, denoise 1.0, 8 шагов, CFG 1 → апскейл; режим качества — как в §4 |
| **Удаление/замена объекта** | см. ниже |
| **Ремонт** | маска делится на плитки 768 px (+ поле 128 px, только плитки, задевающие маску); каждая плитка: Klein img2img с постоянным промптом «убрать царапины, пыль, трещины», сила 0.3–0.9 (по умолчанию 0.8), один seed на все плитки; исправленный центр вклеивается через расширенную растушёванную маску |
| **Коррекция**, **Формат/рамка/подпись**, **Экспорт** | локальная обработка на Go (`internal/adjust`, `internal/finish`), без сервера |
| **Рецепты** | сохранённый список шагов эффектов/образов + значения коррекции (`post_recipes`); применение выполняет шаги по порядку |

**Удаление/замена объекта** (`EditObject`):

1. Если пользователь не вписал объект, приложение рисует на фото красный контур маски, уменьшает до ≤1024 px и спрашивает vision-модель «какой объект внутри красного контура?» (короткое словосочетание).
2. Инструкция: «Remove X completely. Fill the area with the natural background…» или «Replace X with Y…».
3. Klein img2img с референсом по всему фото, 4 шага, denoise 1.0.
4. `maskcomp.Composite` сохраняет оригинал вне изменения: картинка делится на клетки 8 px; клетки внутри маски берутся из правки; изменённые клетки (средняя разница > 28), связанные с маской, тоже; край растушёвывается на 2 клетки.

## 6. Защита памяти

Перед каждым заданием SD (`MemoryGuard.EnsureHeadroom`), если `llm_auto_unload` не `false`:

1. Спросить у сервера, какие LLM-модели загружены; нет ни одной → продолжить.
2. Прочитать свободные VRAM и RAM из `/api/sd/memory`.
3. Нужно: 12 ГиБ VRAM для «тяжёлых» моделей (тот же список имён, что у прозаических), иначе 8 ГиБ, и 10 ГиБ RAM.
4. Не хватает → попросить сервер выгрузить все LLM-модели, ждать до 15 с, затем запустить задание в любом случае.

## 7. Очередь приложения (вкладка «Обработка»)

Таблица `job_queue`; типы `txt2img`, `from_image`, `compound`, `look`, `edit`. Один обработчик выполняет одно задание за раз. MCP-сервер эту очередь не использует.

```
Enqueue ──> pending ──взять──> running ──успех────> completed
               ▲                  │
               │ ошибка с повтором,│ другая ошибка / отмена
               │ попытки остались ▼
               └── (пауза) ───── failed / cancelled
                                  │
           попытки кончились ──> paused ──«Продолжить»──> pending (retry_count = 0)
```

- **Выбор задания**: самое старое `pending`, у которого прошло `next_retry_at`; задания, уже начатые раньше, идут первыми. Обработчик просыпается при постановке задания и каждые 5 с.
- **Ошибки с повтором**: connection refused/reset, timeout, EOF, «SD is not available», no such host, network unreachable. Пауза `5 с × 2^повтор`, не больше 60 с: на деле 10 и 20 с. На третьей неудаче (`max_retries` = 3) задание переходит в `paused`.
- **Продолжение после перезапуска**: каждый вызов сервера из задания очереди получает `client_ref = <install_id>:q<id задания>:s<номер шага>:<хеш запроса>`. При повторном запуске те же шаги дают те же ref, и сервер возвращает уже идущее или готовое задание вместо нового.
- **Ответы LLM** задания сохраняются в `data/queue-llm/<id задания>.json` и при повторном запуске берутся оттуда, поэтому промпт не меняется. Неудачный вызов LLM сохраняется, только когда начинается следующий шаг SD.
- **Приложение закрыли**: выполняемое задание возвращается в `pending` без траты попытки; его задания на сервере продолжают работать. **Приложение упало** (при старте задание всё ещё `running`): это считается попыткой — возврат в `pending` с паузой или `paused`, если попытки кончились.
- **Отмена**: выполняемое задание прерывается (задания на сервере отменяются) и помечается `failed` «cancelled by user»; ожидающее становится `cancelled`. «Пауза» перестаёт брать новые задания.
- **Уборка**: когда задание завершилось, упало или отменено, приложение удаляет его задания на сервере (по префиксу `client_ref`) и файл ответов LLM.

## 8. Фильтры галереи

`ListHistory` (`internal/preset/history.go`) работает по всем `session_items` всех сессий.

1. Один SQL-запрос считает для каждого элемента: `kind` по `source` (generate, from_image, pipeline, edit = edit/look/object/repair, stylist, editor, other), `model_name` и `label` из JSON `meta` (если подписи нет — имя пресета, только для генераций), `shape` (альбом/портрет, если одна сторона длиннее больше чем на 5 %, иначе квадрат; unknown без размера).
2. Поиск по промпту — в SQL: ASCII → `LIKE`; не ASCII → `instr(ic_lower(prompt), ?)`. `ic_lower` — функция на Go, зарегистрированная в SQLite, потому что `lower()` в SQLite меняет регистр только у ASCII.
3. Остальные фильтры — в Go: группы (сессии), модели, подписи, типы, формы, диапазон дат.
4. Счётчики: для каждого фильтра считаются с учётом всех остальных фильтров, кроме него самого. Выбранные значения остаются в списке даже со счётчиком 0. Периоды («всё» плюс даты начала от фронтенда) считаются так же, без учёта фильтра дат.
5. Страница: по умолчанию 120 элементов, максимум 500, новые первыми.

## 9. Сессии

- Каждый результат сохраняет `AddToSession`: файл в `data/sessions/<id сессии>/`, миниатюра 128 px в `data/thumbs/<id сессии>/`.
- Новый элемент становится активным в сессии (`is_active`, один на сессию); `session_active` хранит текущую сессию.
- `meta` (JSON) хранит id пресета, модель, подпись, цепочку пайплайна и исходный элемент.
